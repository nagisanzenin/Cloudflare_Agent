# D1 (serverless SQLite)

> **Use when:** a Worker needs relational data, SQL queries, schema migrations, or you must back up / restore / export a D1 database.
> **Verified:** 2026-10-05 against the sources at the bottom. Re-verify anything older than 90 days.

## Default path

Legend: **[REMOTE]** = touches the production database on Cloudflare. **[LOCAL]** = touches only the local SQLite file used by `wrangler dev`.

1. Create the database and let Wrangler write the binding. **[REMOTE]** (creates a resource)
   ```sh
   npx wrangler d1 create my-db --binding DB --update-config
   # optional: --location weur|eeur|apac|oc|wnam|enam   or   --jurisdiction eu
   ```
2. Create a migration file (local file only, no database contact).
   ```sh
   npx wrangler d1 migrations create my-db create_users_table
   # writes migrations/0000_create_users_table.sql ; put your SQL in it
   ```
3. Apply and test locally. **[LOCAL]**
   ```sh
   npx wrangler d1 migrations apply my-db --local
   npx wrangler d1 execute my-db --local --command="SELECT name FROM sqlite_schema WHERE type='table'"
   npx wrangler dev
   ```
4. Before touching production, record a restore point. **[REMOTE]** (read-only)
   ```sh
   npx wrangler d1 time-travel info my-db        # prints the current bookmark; save it
   ```
5. Apply to production, then deploy. **[REMOTE]**
   ```sh
   npx wrangler d1 migrations list my-db --remote     # shows unapplied migrations
   npx wrangler d1 migrations apply my-db --remote    # COST: rows written are billed
   npx wrangler deploy
   ```

Other commands:

```sh
npx wrangler d1 execute my-db --local  --file=./schema.sql                 # [LOCAL]
npx wrangler d1 execute my-db --remote --file=./schema.sql                 # [REMOTE] COST
npx wrangler d1 execute my-db --remote --command="SELECT COUNT(*) FROM users"   # [REMOTE] COST (rows read)
npx wrangler d1 execute my-db --remote --json --yes --command="..."        # machine-readable, no prompt
npx wrangler d1 export my-db --remote --output=./database.sql              # [REMOTE] blocks other queries while it runs
npx wrangler d1 export my-db --remote --output=./schema.sql --no-data
npx wrangler d1 export my-db --remote --output=./data.sql --no-schema
npx wrangler d1 export my-db --remote --table=users --output=./users.sql
npx wrangler d1 export my-db --local  --output=./local.sql                 # [LOCAL]
npx wrangler d1 info my-db                                                 # [REMOTE] read-only; size, version
npx wrangler d1 insights my-db --time-period 1d --sort-by time --limit 5   # [REMOTE] read-only; slow queries
npx wrangler d1 time-travel info my-db --timestamp="2026-10-05T08:00:00+00:00"   # bookmark for a past time
```

- **DESTRUCTIVE** `npx wrangler d1 time-travel restore my-db --timestamp=<UNIX_OR_RFC3339>` (or `--bookmark=<BOOKMARK>`): **[REMOTE]** overwrites the database in place and cancels in-flight queries. The output prints the previous bookmark; restoring to that bookmark undoes the restore.
- **DESTRUCTIVE** `npx wrangler d1 delete my-db` (`--skip-confirmation` / `-y`): **[REMOTE]** deletes the database.
- Import = `d1 execute --file` with a SQLite-compatible `.sql` file. Remove `BEGIN TRANSACTION` and `COMMIT;` from the dump first. MySQL/Postgres dumps do not import.

## Config

```jsonc
{
	"d1_databases": [
		{
			"binding": "DB",
			"database_name": "my-db",
			"database_id": "<UUID>"
		}
	]
}
```

Optional keys on the same object: `"migrations_dir": "migrations"`, `"migrations_table": "d1_migrations"`, `"preview_database_id": "<UUID>"`, `"remote": true` (makes `wrangler dev` use the production database).

## Code

```ts
export default {
	async fetch(request, env): Promise<Response> {
		// Prepared statement. Parameters: anonymous `?` or ordered `?1`, `?2`. Named parameters are not supported.
		const stmt = env.DB.prepare("SELECT * FROM users WHERE org = ?1 AND active = ?2").bind("acme", 1);

		const { results, meta, success } = await stmt.run();   // D1Result: all rows + meta.rows_read / rows_written
		const row = await stmt.first();                        // first row object, or null
		const email = await stmt.first("email");               // one column of the first row
		const arrays = await stmt.raw({ columnNames: true });  // rows as arrays; first row = column names

		// batch(): one round trip, runs as a transaction; any failure rolls back the whole batch
		const insert = env.DB.prepare("INSERT INTO users (email, org) VALUES (?, ?)");
		const batchResults = await env.DB.batch([
			insert.bind("a@example.com", "acme"),
			insert.bind("b@example.com", "acme"),
		]);

		// exec(): raw SQL, no bindings, returns { count, duration }. Use only for trusted maintenance SQL.
		await env.DB.exec("CREATE TABLE IF NOT EXISTS audit (id INTEGER PRIMARY KEY, note TEXT)");

		return Response.json({ results, row, email, arrays, batchResults, meta, success });
	},
} satisfies ExportedHandler<Env>;
```

`run()` is the documented method that returns rows; the docs call it "functionally equivalent" to `all()`, which still works as an alias.

Read replication (Sessions API). Without `withSession()` every query goes to the primary.

```ts
// "first-unconstrained" (default): first query may hit any replica. "first-primary": first query hits the primary.
const bookmark = request.headers.get("x-d1-bookmark") ?? "first-unconstrained";
const session = env.DB.withSession(bookmark);                  // synchronous
const { results, meta } = await session.prepare("SELECT * FROM users").run();
const response = Response.json({ results, servedBy: meta.served_by_region, primary: meta.served_by_primary });
response.headers.set("x-d1-bookmark", session.getBookmark() ?? "");   // client sends it back next request
return response;
```

Enable replication: dashboard > D1 database > **Settings** > **Enable Read Replication**, or REST `PUT /accounts/{account_id}/d1/database/{database_id}` with `{"read_replication": {"mode": "auto"}}` (`"disabled"` to turn off; replicas can keep serving for up to 24 hours).

## Verify

```sh
npx wrangler d1 migrations list my-db --remote        # expect: no unapplied migrations
npx wrangler d1 execute my-db --remote --command="SELECT name FROM sqlite_schema WHERE type='table' ORDER BY name"
npx wrangler d1 info my-db                            # expect: version: production (required for Time Travel)
```

In code, check `meta.rows_read` on hot queries: a number near the table size means a missing index.

## Gotchas

- The docs disagree on the default target of `d1 execute` when neither flag is given (get-started says local; local-development says remote). ALWAYS pass `--local` or `--remote` explicitly on `execute`, `export`, `migrations apply` and `migrations list`.
- `migrations apply` prompts for confirmation interactively; in CI or any non-interactive shell the prompt is skipped and the migrations run. A failed migration is rolled back and the previous one stays applied.
- `wrangler dev` uses a separate local database that persists between runs. It never sees production data unless the binding sets `"remote": true`.
- Each database is single-threaded: throughput = 1 / query duration. Too many concurrent requests queue, then fail with an "overloaded" error. Design for many small databases (per tenant) instead of one large one.
- Rows read are billed on rows SCANNED, not rows returned. A filter on an unindexed column scans the table. Add indexes (an index adds one written row per write to an indexed column).
- Limits apply to each statement inside `batch()`.
- `d1 export` does not work on databases with virtual tables (FTS5): drop them, export, recreate. A running export blocks other requests.
- Integers above JavaScript's 52-bit precision lose precision on read.
- Time Travel is always on and free; bookmarks older than the retention window are invalid. Max 10 restores per 10 minutes per database.
- `served_by_region` and `served_by_primary` are `undefined` under local `wrangler dev`.
- Use `PRAGMA defer_foreign_keys = true` inside a migration that must temporarily violate foreign keys.
- Drizzle-style nested migration folders need `migrations_pattern` (with `migrations_dir` set); in that layout generate migrations with the ORM, not `wrangler d1 migrations create`.

## Limits and cost

| | Free | Workers Paid |
| --- | --- | --- |
| Rows read | 5 million/day | 25 billion/month included, then $0.001/million |
| Rows written | 100,000/day | 50 million/month included, then $1.00/million |
| Storage | 5 GB total | 5 GB included, then $0.75/GB-month |
| Databases per account | 10 | 50,000 |
| Max database size | 500 MB | 10 GB (cannot be increased) |
| Max storage per account | 5 GB | 1 TB |
| Time Travel window | 7 days | 30 days |
| Queries per Worker invocation | 50 | 1,000 |

Same on both plans: 30 s max query duration, 100 KB max SQL statement, 100 bound parameters per query, 2 MB max row / string / BLOB, 100 columns per table, 5 GB max `d1 execute --file` import.

No charge for egress, idle databases (scale to zero), Time Travel history, restores, or read replicas (replica queries bill as normal rows read). On Free, hitting a daily limit makes queries fail until 00:00 UTC.
